# 설계

설계서는 코드의 정본이다. 이 스킬은 설계서를 바꾸는 유일한 경로다.

## 순서

1. **근거를 찾는다.** 요청이 `docs/requirements.md` 의 어느 FR · NFR 에서 오는지 적는다. 없으면 요구사항부터 고칠지 사용자에게 묻는다. 요구사항에 없는 기능을 설계서에 넣지 않는다.
2. **영향을 본다.** 바뀌는 규칙 ID, 흐름(2절), 이벤트(2.4), 설정(5절)을 나열한다.
3. **초안을 보여 준다.** 파일을 고치지 않고 바뀔 부분만 보여 준다.
   * 새 규칙은 다음 번호를 쓴다. 지운 번호는 다시 쓰지 않는다.
   * 규칙마다 "위반 시" 를 적는다. 무엇이 깨지는지 못 적으면 규칙이 아니다.
   * 규칙마다 4절 테스트 사항에 줄을 더한다. 층(단위 · 그래프 · API · 통합)을 정한다.
4. **승인을 받는다.** 「반영해」를 받은 뒤에만 파일을 고친다.
5. **검사한다.** `scripts/check.sh` 를 돌린다. 테스트 사항에 더한 규칙이 아직 테스트로 덮이지 않았으면 커버리지 검사가 실패하는 것이 정상이다 — `implement` 스킬로 넘긴다.

## 쓰는 법

* 평이한 한국어. 용어는 먼저 정의하고 쓴다.
* 한 사실은 한 곳에만 적는다. 다른 문서가 같은 것을 말해야 하면 가리킨다.
* "왜" 를 적는다. 버린 대안이 있으면 버린 이유를 적는다 (`docs/architecture.md` 3절 형식).
