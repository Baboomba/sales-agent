# 코드 아키텍처

코드를 어떻게 나누는지의 정본이다. 시스템 구성과 기술 선택의 근거는 [아키텍처](../architecture.md)가, 작성 규칙은 [코드 컨벤션](code-style.md)이 갖는다.

`.claude/rules/` 의 규칙 파일은 이 문서의 축약본이다. 둘이 다르면 이 문서가 맞다.

## 1. 계층은 다섯이다

```text
backend/app/
  main.py            조립 루트
  config.py          설정
  <도메인>/
    model/           모델 — 도메인의 기본 객체
    rules/           규칙 — 모델만 보고 판단하는 순수 함수
    dependency/      의존성 — 바깥에서 받는 것의 인터페이스
      impl/          그 구현 — 바깥(언어 모델 · SQL 방언 · DB)을 아는 유일한 자리
    usecase/         유스케이스 — 흐름 하나
    api/             API — HTTP 경계와 DTO
```

**도메인이 최상위다.** 계층으로 먼저 가르지 않는다 — 한 도메인을 고치려고 여러 폴더를 돌아다니지 않게 한다. 지금 도메인은 `query`(질의) 하나다.

**계층은 이 다섯뿐이다.** 다섯 어디에도 맞지 않아 보이는 것이 생기면 새 폴더를 만들지 않고, 아래 2절의 기준으로 다섯 가운데 하나에 넣는다.

## 2. 계층

### 2.1 모델 — 모든 것의 기반

**설계서 5절의 모델이 그대로 온다.** 업무의 말로 된 도메인 객체다 — 질의 도메인이면 질문 · 표와 열 · 생성 SQL · SQL 구성 · 판정 · 실패 · 질의 진행 · 실행 결과 같은 것이다.

* **데이터 형태만 가진다.** `@dataclass(frozen=True)` 로 쓰고 **메서드를 두지 않는다.** 검증 · 계산 · 판정은 전부 규칙으로 간다.
* **아무것도 import 하지 않는다.** 표준 라이브러리와 같은 도메인의 다른 모델까지다. 프레임워크(LangGraph · FastAPI) · 바깥 라이브러리(sqlglot) · 의존성 · DTO 를 모른다.
* **모델은 바깥의 모양을 따르지 않는다.** 그래프 상태의 모양, 응답(JSON · SSE)의 모양, DB 표의 모양, SQL 방언은 모델이 아니다. 그것들을 모델로 옮기고 모델에서 되돌리는 일은 의존성 구현과 API 가 한다.
* **용어는 모델에 둔다.** 업무 정의(매출의 정의, 표 · 열의 업무 설명)와 열거(실패 종류 · 판정 단계)는 모델의 일부다. 그 용어들을 엮은 표(예: 허용할 구문 목록)는 규칙에 둔다.

**왜 메서드를 두지 않나.** 규칙을 모델에 두면 그 규칙이 쓰는 것까지 모델로 끌려온다. 그리고 규칙 가운데 상당수는 모델 하나로 판정되지 않는다 — 다음에 무엇을 할지는 질의 진행과 판정과 한도를 함께 본다. 절반은 메서드, 절반은 함수가 되면 규칙이 어디 있는지 매번 찾게 된다.

**모델이 잘못되면 위의 모든 계층이 엉킨다.** 그래서 모델은 코드보다 설계서에서 먼저 정한다 (`design` 스킬).

### 2.2 규칙 — 모델만 보고 판단한다

**설계서 3절의 비즈니스 규칙이 그대로 온다.** 순수 함수로 쓴다.

* **모델과 인자만으로 결정된다.** 파일 · 네트워크 · 시각 · 난수 · 바깥 라이브러리를 쓰지 않는다. 시각 · 한도처럼 바깥에서 오는 값은 인자로 받는다.
* **import 는 모델까지다.**
* 함수의 문서 문자열 첫 줄에 규칙 ID 를 적는다. 테스트가 그 ID 로 대응한다 (NFR-007).
* 규칙 하나가 함수 하나일 필요는 없지만, **규칙 하나는 한 파일에서만 판단한다.**

**판단은 규칙에만 있다.** SQL 이 안전한지, 결과가 잘렸는지, 재시도할지 실패로 끝낼지는 규칙이 정한다. 유스케이스는 규칙의 답을 따라 흐름을 옮길 뿐이고, 의존성 · API 는 판단하지 않는다.

**바깥의 글을 직접 해석하지 않는다.** 규칙은 SQL 글을 파싱하지 않고 **SQL 구성 모델**을 본다. 규칙이 바깥의 말(방언 · 오류 문구 · 출력 형식)에 묶이면, 바깥이 바뀔 때 업무 규칙까지 바뀐다.

### 2.3 의존성 — 바깥을 모델로 옮긴다

유스케이스가 바깥에서 받는 것이다. **인터페이스와 구현을 나눈다.**

| 자리 | 담는 것 | import 할 수 있는 것 |
|---|---|---|
| `dependency/<이름>.py` | 인터페이스(`typing.Protocol`)와 그것이 던지는 실패 | 모델 |
| `dependency/impl/<이름>.py` | 구현. 바깥 라이브러리 · 서버 · 파일을 아는 유일한 자리 | 모델 · 인터페이스 · 바깥 라이브러리 |

질의 도메인의 의존성은 셋이다.

| 의존성 | 하는 일 | 구현이 아는 바깥 |
|---|---|---|
| 생성기 | 질문 · 표 · 직전 판정을 받아 **생성 SQL** 을 돌려준다. 프롬프트 조립과 모델 출력 해석은 구현 안의 일이다 | 언어 모델(Ollama), 프롬프트 형식, 출력 형식(JSON) |
| SQL 분석기 | 생성 SQL 을 **SQL 구성** 으로 옮기고, 행 상한을 붙인 SQL 을 만든다 | SQL 방언(SQLite), sqlglot |
| 매출 DB | 표 · 열을 돌려주고, SQL 을 읽기 전용으로 실행해 **실행 결과** 를 돌려준다. DB 의 거부 · 오류 문구는 **실패** 로 옮긴다 | SQLite |

* **바깥의 예외 · 모양이 구현 밖으로 나가지 않는다.** `httpx` · `sqlite3` · `ollama` · sqlglot 의 예외와 객체는 구현 안에서 모델 · 실패로 옮긴다.
* **구현은 판단하지 않는다.** 옮기기만 한다. 예: SQLite 의 `no such column: o.x` 를 「별칭 `o` 의 표가 없음」이라는 실패로 옮기는 것까지가 구현이고, 그것을 어떻게 안내할지(`QRY-R015`)는 규칙이다.

### 2.4 유스케이스 — 흐름 하나

**흐름 하나가 유스케이스 하나다.** 질의 도메인은 둘이다 — 질의(질문 → 생성 → 판정 → 실행)와 보조 조회(표 · 열, 예시 질문).

* 의존성을 **생성자로 받는다** (인터페이스만 안다. `impl` 을 import 하지 않는다).
* 의존성을 불러 모델을 받고, **규칙에 판단을 맡기고**, 그 답대로 다음으로 넘어간다.
* 흐름을 이끄는 도구(LangGraph)는 유스케이스 안의 일이다. 그래프 상태는 유스케이스 안에만 있고, 밖으로는 **모델**을 낸다.
* 수(한도 · 횟수)는 생성자 인자로 받는다. 설정 객체를 직접 읽지 않는다.

### 2.5 API — 경계

* HTTP 요청을 받아 **유스케이스만 부른다.** 규칙 · 의존성을 직접 부르지 않는다.
* **DTO 는 API 가 가진다.** 요청 모양, 응답 · SSE 이벤트 모양이 여기 있다. 유스케이스가 낸 모델을 DTO 로 옮기는 것도 여기서 한다.
* 판단하지 않는다. 유스케이스가 거부한 입력을 422 로 옮기는 것처럼, 답의 모양만 바꾼다.

## 3. 의존 방향

```text
api ──▶ usecase ──▶ rules ──▶ model
                 │              ▲
                 └──▶ dependency ┤
                         ▲       │
                 dependency/impl ┘

main ──▶ api · usecase · dependency/impl · config
```

* **안쪽으로만 향한다.** 모델은 아무것도 모르고, 규칙은 모델만 안다.
* **`dependency/impl` 을 아는 곳은 `main` 하나다.** 유스케이스는 인터페이스만 받는다. Ollama 를 다른 모델 서버로, SQLite 를 다른 DB 로 바꿔도 모델 · 규칙 · 유스케이스는 그대로다.
* **이 방향은 사람이 지키지 않는다.** `import-linter` 계약이 `scripts/check.sh` 에서 검사한다 (`backend/pyproject.toml`).

| 계약 | 막는 것 |
|---|---|
| 계층 | `api → usecase → rules → model` 의 역방향 import |
| 모델은 아무것도 모른다 | 모델이 같은 도메인의 모델 밖을 import |
| 규칙은 모델만 안다 | 규칙이 의존성 · 유스케이스 · 바깥 라이브러리를 import |
| 구현은 조립 루트만 안다 | `api` · `usecase` · `rules` · `model` 이 `dependency.impl` 을 import |

**경계를 피하려고 import 를 함수 안으로 숨기지 않는다.** 검사를 통과해도 구조가 무너진 것이다.

## 4. 실패를 나누는 법

실패도 모델이다. 종류마다 다루는 곳이 다르다.

| 실패 | 예 | 누가 만드나 | 누가 판단하나 |
|---|---|---|---|
| 다시 만들면 나을 수 있는 실패 | 쓰기 SQL, 허용되지 않은 표, 구문 오류, 실행 오류, 출력 형식 오류 | 규칙(판정), 의존성 구현(바깥 오류를 옮김) | 규칙이 재생성할지 끝낼지 정한다 |
| 다시 해도 안 되는 실패 | 모델 서버 장애(연결 · 오류 응답 · 시간 초과) | 의존성 구현 | 규칙이 바로 끝내라고 정한다 |
| 예상하지 못한 실패 | 버그 | — | 유스케이스 입구의 안전망이 로그를 남기고 실패로 끝낸다 |

* **예상한 실패는 예외로 흐름을 끊지 않는다.** 의존성이 실패 모델을 돌려주거나 던지면, 유스케이스가 받아 규칙에 묻고 그 답대로 간다.
* **사유는 사용자에게 보이는 말이다.** 다음 생성에도 붙으므로 무엇을 고치면 되는지가 드러나게 쓴다.

## 5. 설정과 조립 루트

* 수(상한 · 제한 시간 · 횟수)는 코드에 박지 않는다. `config.Settings` 가 환경변수에서 받고, 기본값은 설계서의 설정 절과 같다. 설정끼리의 관계는 `Settings.check()` 가 서버가 뜨기 전에 검사한다.
* `main.create_app` 이 의존성 구현을 만들어 유스케이스에, 유스케이스를 API 에 끼운다. 테스트는 같은 함수에 가짜 의존성을 넘긴다.
* **import 할 때 앱을 만들지 않는다.** 실행은 `uvicorn --factory app.main:app_from_env` 다.

## 6. 화면

### 6.1 계층은 넷이다

**조립은 위에서 아래 한 방향이다.** 아래는 위를 모른다.

```text
frontend/src/
  main.tsx        진입점. App 을 붙인다
  App.tsx         앱 루트. 전역 상태를 감싸고 화면을 붙인다
  index.css       기틀 값(색 · 간격 변수)과 전역 스타일
  pages/          화면 — 그 화면 전용 배치와 상태
  features/       완결된 기능 UI — 그 자체로 한 일을 끝낸다
  entities/       업무 객체 표시 — 상호작용 상태가 없다
  components/     부품 — 도메인을 모른다
  api/            서버를 부르는 자리
  context/        전역 상태
  common/         어느 계층의 것도 아닌 것
```

| 계층 | 뜻 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| **pages** | 화면 하나가 폴더 하나 (질의 화면) | 아래 묶음들을 **배치**한다. 배치와 분량이 여기 몫이다 | 여러 화면이 쓰는 로직 · 업무 판단 |
| **features** | 그 자체로 **하나의 일을 끝내는** UI (질문하고 진행을 받아 보기 · 데이터 목록 보기) | 조립 · 상태 · 순수 로직 · 서버 호출 | 화면 배치 |
| **entities** | 업무 객체 **하나를 보여주는** 것 (진행 단계 · 실행한 SQL · 실행 결과 표 · 표와 열) | 받은 값을 그린다 · 표시용 계산 | 상호작용 상태 · 서버 호출 |
| **components** | 도메인을 모르는 부품 (버튼 · 입력 · 표 · 배지) | 마크업 · 스타일 · `className` 통과 | 업무를 아는 것 |

**어디에 두는지 가리는 순서.** 서버 응답을 모르면 → `components`. 응답 하나를 그리면 → `entities`. 그 자체로 한 일을 끝내면 → `features`. 화면이 되면 → `pages`.

**묶는 이름은 일반화한 것이어야 한다.** 버튼 · 입력 · 표처럼 **무엇인지**로 묶고, 쓰임새로 묶지 않는다 — 「질문입력」 · 「검색입력」은 둘 다 입력이다. 다른 점은 받는 값으로 가른다. `entities` · `features` 도 업무 객체나 기능의 이름으로 묶고, 놓이는 화면 이름을 붙이지 않는다.

### 6.2 한 묶음의 구성

묶음 하나는 **렌더 · 상태 · 순수 로직** 셋으로 갈리고, 관심사는 늘 자기 파일로 나눈다.

| 관심사 | 파일 |
|---|---|
| 렌더 · 조립 | `<묶음>.tsx` — 파일 이름이 그 안의 컴포넌트 이름이다 |
| 상태 | `hooks.ts` |
| 순수 로직 | `service.ts` |
| 스타일 | `<묶음>.module.css` |
| 테스트 | `<묶음>.test.tsx`, 여럿이면 `__test__/` |
| 내보내는 것 | `index.ts` — 바깥은 이것으로만 가져다 쓴다 |

```text
components/Button/          Button.tsx · Button.module.css · Button.test.tsx · index.ts
entities/query/QueryStep/   QueryStep.tsx · QueryStep.module.css · QueryStep.test.tsx · index.ts
features/AskQuery/          AskQuery.tsx · AskQuery.module.css · hooks.ts · service.ts · index.ts · __test__/
pages/Query/                Query.tsx · Query.module.css · index.ts
```

* **`components` · `entities` 는 `hooks.ts` · `service.ts` 가 없다.** 상호작용 상태가 없고, 표시용 계산은 대개 함수 하나라 같은 파일에 둔다.
* **`features` 부터 `hooks.ts` 와 `service.ts` 가 생긴다.** 훅 정의와 순수 함수를 `.tsx` 에 두지 않는다. 열림 · 선택처럼 표현만 바꾸는 한 줄짜리 상태는 그대로 둬도 된다.
* **엔티티는 업무 객체로 한 번 더 묶는다** — `entities/query/` 안에 조각마다 폴더가 선다.
* **화면만 쓰는 조각은 그 화면 폴더 안에** 둔다. 두 번째 화면이 쓰게 되면 `features` 로 올린다.
* **내보내지 않는 조각은 제 파일을 갖지 않는다.** 같은 파일 안에 둔다. 파일이 커져 읽기 어려워지면 묶음 안에 `components/` 를 만들어 조각을 다 옮긴다.
* **묶음 안의 디렉터리는 `components/` 와 `__test__/` 둘뿐이다.**
* **없는 관심사는 파일을 만들지 않는다.** 빈 파일이나 넘기기만 하는 파일을 두지 않는다.
* **`service.ts` 는 라이브러리를 모른다.** React 도 서버 호출도 부르지 않는다. 그래야 아무것도 띄우지 않고 테스트된다.

### 6.3 서버 호출과 업무 모델

**`api/` 한 곳으로 모은다.** 화면마다 직접 부르지 않는다.

| 뜻 | 자리 |
|---|---|
| 부르는 함수 | `api/<도메인>.ts` — 주소 하나에 함수 하나 |
| 공통 처리 | `api/client.ts` — 요청 · 오류 종류 판정 · 스트림 읽기 |
| SSE 해석 | `api/sse.ts` — 순수 함수 |
| 응답 타입 | `api/types/` — 서버 DTO 와 같은 타입 |
| 정해진 값 | `common/values.ts` — 이벤트 이름 · 단계처럼 서버가 설계서의 이름으로 내는 값. 응답 타입과 엔티티가 함께 쓴다 |

**클라이언트에 업무 모델을 두지 않는다.** 업무는 서버가 소유한다.

* 응답을 **다른 이름으로 감싸 다시 만들지 않는다.** 서버 DTO 타입을 그대로 쓴다.
* **판정 · 계산 · 집계를 화면에서 하지 않는다.** `service.ts` 가 하는 것은 보여주기 위한 손질이다 — 자릿점, 라벨. **숫자를 반올림하지 않는다** (NFR-002).
* 화면에만 있는 상태(입력 중인 질문 · 진행 중 여부)는 타입을 따로 둔다. 응답과 수명이 다를 때만 만든다.

### 6.4 상태의 자리

| 뜻 | 자리 |
|---|---|
| 서버에서 온 것 | 그것을 부르는 `features` 의 `hooks.ts` |
| 화면에만 있는 것 — 입력 중인 값 · 진행 중 · 열림 | `hooks.ts`, 표현만 바꾸는 것은 컴포넌트 안 |
| 여러 화면이 함께 쓰는 것 | `context/<이름>/provider.tsx`. `context/provider.tsx` 하나가 전부를 조립하고 `App` 이 그것 하나만 감싼다 |

**서버에서 온 것을 전역에 담지 않는다.** 전역에 두는 것은 화면 전체가 함께 보는 것뿐이다.

### 6.5 이름

* **컴포넌트를 담은 폴더와 파일은 파스칼**(`Button/Button.tsx`), **계층 · 엔티티 묶음 · 그 밖의 파일은 소문자**(`components/` · `entities/query/` · `hooks.ts`).
* **제 폴더 밖은 `@/` 로 가리킨다.** 올라가는 상대 경로(`../`)를 쓰지 않는다 — 계층을 넘는지가 경로 모양으로 드러나야 정적 분석이 잡는다.

### 6.6 경계를 지키는 방법

| 뜻 | 방법 |
|---|---|
| 조립 방향 | **정적 분석(ESLint)이 잡는다.** `entities` 가 `features` 를, `components` 가 `api` 를 가져다 쓰지 못하게 막는다 |
| `api/` 밖에서 서버 부르기 | `fetch` 를 `api/` 밖에서 쓰지 못하게 막는다 |
| 올라가는 상대 경로 | 막는다. 제 폴더 밖은 `@/` |
| 묶음 속을 바로 가져다 쓰기 | 막는다. `components` · `entities` · `features` 는 `index.ts` 로만. 테스트는 속을 들여다본다 |
| 접근성 | `jsx-a11y` 규칙을 켠다 |

전부 `scripts/check.sh` 의 린트에 묶는다. 경고로 두지 않는다.

**스타일은 묶음마다 CSS Modules.** 색 · 간격은 `index.css` 의 변수만 쓴다. UI 라이브러리를 들이지 않는다. 화면의 배치(격자 · 간격)는 `pages` 가, 묶음 안의 생김새는 그 묶음이 갖는다.

## 7. 바꿀 때

* 계층의 책임을 바꾸면 이 문서와 경계 검사(서버 `import-linter` 계약, 화면 ESLint 규칙)를 함께 고친다.
* 도메인을 더하면 1절의 모양을 따르고, 계약에 그 도메인을 더한다.
* 모델을 바꾸는 일은 설계서 5절에서 시작한다.
