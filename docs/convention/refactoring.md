# 리팩토링 규칙

동작은 그대로 두고 **구조만 나아질 곳**을 찾는 기준이다. `refactor-review` 스킬이 이 문서로 검사한다. 기능을 더하거나 바꾸는 것은 리팩토링이 아니다.

판단의 근거는 [코드 아키텍처](code-architecture.md)와 [코드 컨벤션](code-style.md)이다. 이 문서는 무엇을 문제로 보는지와 어떻게 가르는지를 정한다. 지적의 심각도 · 다시 검사의 범위 · 멈추는 기준은 [검사 운영 규칙](review.md)이 정한다.

## 1. 검사 항목은 여섯이다

항목마다 **판정 질문**이 있다. 질문에 답할 수 없으면 지적하지 않는다.

### 1.1 단일 책임 위반

**판정 질문: 이 함수 · 파일이 바뀌는 이유가 둘 이상인가.**

* 한 함수가 서로 상관없는 일을 둘 이상 한다 — 바깥을 읽고, 판단하고, 문구를 짓는다.
* **판단이 규칙 밖에 있다.** 유스케이스 · 의존성 구현 · API 가 판정한다. 판단은 규칙에만 있다 (코드 아키텍처 2.2).
* **모델에 메서드가 생겼다.** 검증 · 계산 · 판정은 규칙으로 간다 (코드 아키텍처 2.1).
* **규칙이 바깥의 글을 해석한다.** SQL 글 · 오류 문구 · 출력 형식을 규칙이 직접 읽는다. 의존성 구현이 모델로 옮기고 규칙은 모델을 본다.
* **모델이 바깥의 모양을 따른다.** 그래프 상태 · 응답 · DB 표의 모양이 모델에 들어왔다.
* **화면 계층을 건너뛴다.** `entities` 가 서버를 부르거나 상태를 갖는다, `pages` 에 여러 화면이 쓸 로직이 있다, `features` 의 `.tsx` 에 훅 정의 · 순수 함수가 있다 (코드 아키텍처 6절).

### 1.2 비효율

**판정 질문: 같은 결과를 더 적은 왕복 · 계산으로 낼 수 있는가.**

* 한 번에 할 수 있는 DB · 모델 서버 왕복을 여러 번 한다.
* 서로 기다릴 일 없는 바깥 호출을 차례로 기다린다.
* 이미 아는 것을 다시 묻는다 — 바로 앞에서 받은 스키마를 또 읽는다, 같은 분석을 두 번 한다.
* 반복마다 목록을 새로 펼쳐 만든다 — 크기에 따라 제곱으로 는다.
* 결과를 메모리로 다 가져와 센다 — DB 가 세게 한다.

### 1.3 쓰이지 않거나 일어나지 않는 분기

**판정 질문: 이 갈래에 닿는 입력을 실제로 만들 수 있는가.**

* 앞에서 이미 막아 닿을 수 없는 `if` · `or` · `raise`.
* 부르는 쪽이 이미 걸러 들어올 수 없는 값의 확인.
* 타입상 늘 있는 값에 붙인 대체값.
* 다른 규칙이 이미 막는 상태를 거르는 조건.
* 쓰이지 않는 함수 · 상수 · 내보내기 · 스타일 클래스.

**닿을 수 없는 갈래는 테스트할 것이 아니라 지울 것이다.**

### 1.4 심각한 하자

**판정 질문: 지금은 통과해도, 데이터 · 사용량이 늘거나 바깥이 실패하면 사고가 나는가.**

* **N+1** — 아래 「N+1」.
* **실패를 조용히 삼킨다** — 잡고 아무것도 하지 않는다, 넓게 잡아 원인을 잃는다. 넓은 `except` 는 유스케이스 입구의 안전망 한 곳뿐이다.
* **바깥의 예외 · 객체가 의존성 구현 밖으로 샌다** — `sqlite3` · `httpx` · sqlglot 의 것이 유스케이스까지 올라온다.
* **확인하고 쓰는 사이에 남이 끼어들 수 있다.**
* **수를 코드에 박았다** — 상한 · 제한 시간 · 횟수.
* **신뢰하지 않는 입력을 검증 전에 쓴다** — 모델이 낸 SQL 을 판정 전에 실행한다.

#### N+1

목록을 하나 얻은 뒤 **항목마다 바깥을 한 번씩 더 부르는 것**이다. 처음 한 번에 항목 수(N)만큼이 붙어 N+1 번이 된다. 항목이 적을 때는 테스트도 통과하고 느리지도 않아서, 데이터가 늘어난 뒤에야 드러난다.

**판정 질문: 항목이 1개일 때와 N개일 때, 바깥을 부르는 횟수가 같은가.** 항목 수만큼 늘어나면 N+1 이다.

**찾는 법.**

| 어디 | 이런 모양 |
|---|---|
| 의존성 구현 | 목록을 읽은 뒤 반복문 안에서 항목마다 DB 에 다시 묻는다 — 표 목록을 읽고 표마다 열 정보를 따로 읽는 것 |
| 유스케이스 | 반복문 안에서 의존성을 부른다 — 받은 목록의 항목마다 생성기 · DB 를 부른다 |
| 화면 (`features` · `hooks.ts`) | 목록을 받은 뒤 항목마다 서버를 부른다. 목록의 항목을 그리는 `entities` 가 서버를 부르는 것은 계층 위반이기도 하다 |

반복문만 찾지 않는다. `map` · 컴프리헨션 · 반복 안에서 부르는 함수 속까지 따라가 바깥 호출에 닿는지 본다.

**고치는 법.** 한 번에 묻는다 — 조인 · `IN` · 묶음 조회로 필요한 것을 한 번에 가져오고, 메모리에서 항목에 나눠 붙인다. 바깥이 묶음 조회를 주지 않으면 의존성 인터페이스에 묶음으로 받는 함수를 더한다. **유스케이스가 항목마다 부르는 모양을 의존성 구현 안으로 숨기지 않는다** — 숨겨도 호출 수는 그대로다.

**테스트로 막는다.** 고친 자리에는 호출 수를 견주는 테스트를 둔다 ([테스트 규칙](testing.md) 7.3).

### 1.5 공용 코드를 쓰지 않은 곳

**판정 질문: 이미 있는 것을 손으로 다시 하고 있는가.**

* 공용 함수 · 부품(`components`) · 정해진 값(`common/values.ts`)에 이미 있는 일을 다시 한다 — 자릿점 표기, 이벤트 이름, 사유 문구.
* 공용 함수를 쓰긴 하는데 맞지 않는 쪽을 골라 손으로 메운다.

### 1.6 중복

**판정 질문: 한 곳을 고치면 다른 곳도 같이 고쳐야 하는가.**

* 같은 코드 · 상수 · 문구가 두 곳 이상에 있다. 한 파일 안의 중복도 넣는다.
* **세 벌이면 공용으로 뽑는다. 두 벌이면** 뽑는 값이 비용보다 큰지 따져 권한다.
* 서로 가져다 쓸 수 없는 자리의 한 줄짜리 중복은 그대로 두는 편이 나을 때가 많다 — 그렇게 권하고 까닭을 적는다.

## 2. 가르기

찾은 것을 셋으로 나눈다.

| 갈래 | 언제 |
|---|---|
| **이 분기에서 고칠 것** | 이 분기가 만들었거나 건드린 코드, 또는 이 분기가 세 번째 사본을 더해 문턱을 넘긴 것 |
| **따로 뺄 것** | 이 분기와 상관없는 도메인 · 화면까지 고쳐야 하는 것. 이슈로 뺀다 (작업 이슈, 종류 `refactor`) |
| **그대로 두기를 권함** | 고치면 타입 · 분기 · 간접이 늘어 얻는 것보다 잃는 것이 큰 것. 까닭을 적는다 |

## 3. 고칠 때 지킬 것

* **동작을 바꾸지 않는다.** 응답 모양 · 사유 문구 · 이벤트 순서가 그대로인지 기존 테스트로 확인한다. **기존 테스트를 고쳐야 통과한다면 동작이 바뀐 것이다** — 멈추고 알린다.
* 인터페이스가 바뀌면(의존성의 모양 등) 가짜와 테스트를 함께 맞춘다.
* 고친 갈래에 테스트가 없으면 더하고, 일부러 망가뜨려 그 테스트가 깨지는지 본다 ([테스트 규칙](testing.md) 4절).
* 설계서가 바뀌어야 하면 설계서부터 고친다 (`design` 스킬, 사용자 확인).
* 끝나면 `scripts/check.sh` 를 돌린다.
