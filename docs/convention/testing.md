# 테스트 규칙

테스트를 어떻게 쓰는지의 정본이다. 계층은 [코드 아키텍처](code-architecture.md)가, 작성 규칙은 [코드 컨벤션](code-style.md)이 갖는다. `test-review` 스킬이 이 문서로 검사한다.

`.claude/rules/backend-test.md` 는 이 문서의 축약본이다. 둘이 다르면 이 문서가 맞다.

## 1. 판정 기준은 하나다

**구현을 통째로 다시 써도 그 테스트가 그대로 통과하는가.** 그리고 **틀린 구현은 통과하지 못하는가.**

앞의 것을 어기면 고칠 필요 없는 변경에 테스트가 깨지고, 뒤의 것을 어기면 테스트가 있어도 결함을 못 잡는다.

## 2. 원칙

1. **동작과 결과를 본다.** 밖에서 관찰할 수 있는 것 — 돌려준 값, 남긴 상태, 낸 이벤트 — 만 단언한다.
2. **구현에 의존하지 않는다.** 내부 호출의 순서와 횟수, 비공개 함수, 내부 자료구조, 구현이 쓰는 문구에 기대지 않는다.
3. **한 테스트가 한 사실을 본다.** 단언 개수가 아니라, 깨졌을 때 이유가 하나로 읽히는가다.
4. **중복을 만들지 않는다.** 같은 판정을 두 자리에서 보지 않는다 — 규칙의 판정은 규칙 테스트가 보고, 유스케이스 테스트는 흐름을 본다.
5. **테스트끼리 의존하지 않는다.** 실행 순서와 남이 남긴 상태에 기대지 않는다.
6. **이름이 실패 원인을 말한다.** 무엇을 했을 때 무엇이 되는지가 이름이다.
7. **설계서에 없는 것도 빠졌는지 본다.** 경계값 · 이상한 입력 · 겹쳐 오는 요청은 설계서가 적지 않는다 (6절).

**예외 — 설계가 성질로 정한 것.** 「실행 뒤에는 생성기를 부르지 않는다」(`QRY-R011`)처럼 설계서가 호출 여부 자체를 규칙으로 정했으면, 호출 횟수로 확인해도 구현 의존이 아니다.

## 3. 자주 어기는 자리

| 이렇게 하면 | 이렇게 한다 |
|---|---|
| **기대값을 계산한다** | **값을 적는다.** 계산하면 구현이 무엇을 내든 같이 따라간다 |
| **구현이 쓰는 상수 · 문구와 견준다** — `UNAVAILABLE_REASON in reason` | **테스트가 넣은 값이 그대로 나오는지 본다** — 가짜가 돌려준 실패의 세부 `"connection refused"` 가 사유에 있는지. 문구는 바뀐다. **예외: 설계서 4절이 안내의 낱말을 정했으면 그 낱말은 본다**(예: `QRY-R015` 「JOIN」, `QRY-R009` 「가벼운」). 낱말이 테스트가 넣은 입력에 없을 때만 확인이 된다 |
| **입력에 이미 있는 글자를 다시 찾는다** — `"SELECT" in validate(sql)` | **결과 전체를 적어 비교한다** — `== "SELECT * FROM stores LIMIT 201"` |
| **몇 번 불렀는지 센다** (설계가 정한 성질이 아닌데) | **무엇이 남았는지 본다.** 한 번에 둘로 나눠 부르는 정상적인 변경까지 깨뜨린다 |
| **예외 메시지 글자로 판정한다** | **예외 타입이나 사유 속성으로 본다** |
| **규칙 ID 만 적고 그 규칙을 보지 않는다** | 규칙이 정한 사실을 확인하는 테스트에만 그 ID 를 적는다. 아니면 ID 를 떼거나 맞는 규칙으로 옮긴다 |

## 4. 혼자 두면 아무것도 못 잡는 단언을 남기지 않는다

**「없다」 · 「비었다」 · 「통과한다」는 늘 그렇게 하는 구현에서도 참이다.** 단언마다 묻는다 — **이 단언, 틀린 구현도 통과하지 않나.**

* **고정 문구에 원래 있는 글자를 찾지 않는다.** 감사 #17 에서 나온 예: 재생성 프롬프트에 `"JOIN"` 이 있는지 보는 단언은, 안내 문구에 원래 JOIN 이 있어서 안내를 붙이지 않는 구현에서도 통과했다. **고정 문구에 없는 값**(테스트가 넣은 별칭, `zzz_receipts` 같은 이름)으로 확인하거나, 붙기 전과 후를 함께 본다.
* **참 거짓만 보지 않는다.** `assert result` · `assert description` 은 비어 있지 않은 아무 값이면 통과한다. 기대값과 비교한다. 사유를 `is not None` 으로만 보면 빈 사유 `""` 도 통과한다.
* **없는 쪽에는 있는 쪽 짝을 둔다.** 「사유가 없으면 붙지 않는다」만 보면 사유를 아예 버리는 구현도 통과한다. 「있으면 붙는다」와 한 테스트에 두거나, 짝이 어디 있는지 이름으로 드러낸다.
* **「통과한다」에도 「거부한다」 짝을 둔다.** 「CTE 이름은 허용한다」만 보면 CTE 가 있으면 모든 표를 여는 구현도 통과한다. 허용하는 조건이 있으면, 그 조건 곁에서도 여전히 거부되는 것을 함께 본다.
* **환경 때문에 저절로 참이 되지 않게 한다.** 시간대 · 정렬 기본값 · 빈 문자열 비교처럼, 우연히 맞는 조건에서 돌지 않는지 본다.

**입력도 틀린 구현을 가를 수 있어야 한다.** 단언이 맞아도, 맞는 구현과 틀린 구현이 같은 답을 내는 입력이면 아무것도 못 잡는다.

* **기본값 · 실제 값과 같은 입력 하나로만 보지 않는다.** 행 상한을 기본값 200 으로만 보면 `201` 을 박아 둔 구현도 통과한다. 허용 표를 실제 표 넷으로만 넘기면 인자를 무시하고 표 이름을 박아 둔 구현도 통과한다. **기본값이 아닌 값, 실제와 다른 값**(`50`, `zzz_sales`)을 함께 넣는다. 대소문자 · 단위처럼 양쪽을 맞춰야 하는 것은 양쪽에 다 넣는다.
* **찾을 대상을 한 자리에만 두지 않는다.** 목록에서 무엇을 찾는 판정인데 대상이 늘 마지막에 있으면, 마지막만 보거나 반복 변수를 덮어쓰는 구현도 통과한다. **처음 · 가운데 · 끝**에 두고, 찾을 것이 여럿이면 둘 이상 넣어 다 나오는지 본다.
* **판정에 쓰여야 할 필드만 그 답을 갖게 한다.** 별칭을 실패 모델의 별칭 필드에서 꺼내야 하는데 세부 글에도 별칭이 있으면, 글을 파싱하는 구현도 통과한다. 다른 필드에서 같은 답이 새어 나오지 않는 입력을 쓴다.

**지적은 꼴로 고친다.** 위 가운데 하나를 지적받으면 그 줄만 고치지 않는다. 같은 꼴을 범위의 모든 테스트에서 찾아 함께 고친다. 줄만 고치면 같은 지적이 다른 파일에서 다시 나온다(#40 에서 다섯 차례 되풀이됐다).

## 5. 테스트에 로직을 넣지 않는다

`if` · 반복 · 계산이 들어가면 그 테스트를 다시 테스트해야 한다. 여러 경우는 `pytest.mark.parametrize` · `it.each` 로 늘어놓는다.

**가짜 구현도 같다.** 가짜는 정해 둔 답을 차례로 돌려주고, 받은 것을 기록하기만 한다. 판단이 붙으면 그 가짜가 검증 대상이 된다.

## 6. 빠진 것을 찾아 더한다

테스트를 다 썼다고 생각한 자리에서 한 번 더 훑는다. 설계서와 대조하는 것만으로는 아래가 나오지 않는다.

| 어디를 보나 | 이런 것 |
|---|---|
| **갈래의 양쪽** | `if` · 삼항 · `or` · `except` 의 양쪽, 각 열거 값 |
| **경계값과 이상한 입력** | 상한 그 값 · 하나 넘은 값, 빈 값, 공백뿐인 값, 닫히지 않은 따옴표 같은 깨진 입력 |
| **바깥이 실패하는 경우** | 연결 실패 · 오류 응답 · 시간 초과 · 예상하지 못한 예외 |
| **쓰는 도구의 함정** | 라이브러리가 예외 계층을 다르게 둔 것(감사 #17 의 `TokenError`), 함수 호출을 표 이름 없이 주는 것 |
| **이름만 걸어 둔 자리** | 규칙 ID 를 적어 놓고 정작 그 판정을 보지 않는 테스트 |

**업무 판단이 빠진 것이면** 설계서에 규칙을 먼저 더하고(사용자 확인) 그 ID 로 테스트한다. 나머지는 규칙 ID 없이 더한다.

## 7. 계층마다 무엇을 보나

### 7.1 서버

| 계층 | 무엇을 보나 | 무엇 없이 | 자리 |
|---|---|---|---|
| **모델** | 테스트하지 않는다. 데이터 형태라 확인할 동작이 없다. 구조는 경계 검사가 본다 | — | — |
| **규칙** | 판정. 모델과 인자를 넣고 답을 본다 | 의존성 · 프레임워크 | `tests/<도메인>/rules/` |
| **유스케이스** | **흐름** — 어느 경로로 갔는지, 무엇을 냈는지, 끝이 무엇인지. 규칙의 판정을 다시 보지 않는다 | 가짜 의존성 | `tests/<도메인>/usecase/` |
| **의존성 구현** | 바깥을 모델 · 실패로 제대로 옮기는지. 바깥이 실제로 있어야 보이는 것(읽기 전용 · 제한 시간) | 순수 라이브러리만 쓰면 단위, 파일 · DB 에 닿으면 통합 | `tests/<도메인>/dependency/` · `tests/integration/` |
| **API** | 입력이 422 로 막히는지, 모델이 DTO · SSE 로 옮겨지는지 | 가짜 의존성으로 조립한 앱 | `tests/<도메인>/api/` |

* **가짜는 도메인마다 한 자리에 둔다** — `tests/<도메인>/fake.py`. 쓰는 테스트 옆에 두면 같은 가짜가 여러 벌 생긴다.
* **목(mock) 라이브러리를 쓰지 않는다.** 의존성이 인터페이스라 가짜를 손으로 쓴다. 목으로 호출 순서와 횟수를 검증하기 시작하면 구현에 의존하는 테스트가 된다.
* **언어 모델을 부르는 테스트를 쓰지 않는다** (NFR-005). 언어 모델의 품질은 테스트가 아니라 평가 세트(`eval` 스킬)가 잰다. CI 에 모델 서버가 없다.
* **통합 테스트는 표시를 붙인다** — `@pytest.mark.integration`. 실제 파일 · DB 에 닿는 것만 여기 둔다.
* **테스트 데이터를 만드는 도구를 미리 만들지 않는다.** 같은 준비가 세 번째 나오면 그때 뺀다.

### 7.2 화면

| 계층 | 무엇을 보나 | 자리 |
|---|---|---|
| **components** | 받은 값대로 그리는지, 접근성(역할 · 이름) | 묶음 옆 `<묶음>.test.tsx` |
| **entities** | 업무 객체를 맞게 그리는지, 표시용 계산(자릿점 · 라벨) | 묶음 옆 `<묶음>.test.tsx` |
| **features** | `service.ts` 의 순수 로직, `hooks.ts` 의 상태 변화, 조립 결과 | 묶음 안 `__test__/` |
| **pages** | 배치뿐이라 대개 테스트하지 않는다. 조각이 빠지지 않았는지 정도 | 화면 폴더 |
| **api** | SSE 해석 같은 순수 함수 | `api/` 안 |

* **화면을 보는 테스트는 사용자가 보는 것으로 찾는다** — 역할 · 이름 · 글자. 클래스 이름 · 내부 구조로 찾지 않는다.
* **서버 응답을 짐작해 짓지 않는다.** 응답 모양은 `api/types/` 의 타입을 따르고, 서버의 이벤트 이름 · 필드와 같아야 한다.

### 7.3 N+1 은 호출 수를 견주어 막는다

N+1 은 테스트가 통과해도 그대로 남는다 — 항목이 적은 테스트 데이터에서는 결과도 맞고 느리지도 않다 ([리팩토링 규칙](refactoring.md) 1.4). 그래서 **바깥을 부른 횟수**를 본다.

* **항목이 1개일 때와 여러 개(3개 이상)일 때 호출 수가 같은지만 본다.**
* **몇 번인지는 단언하지 않는다.** `== 2` 처럼 적으면 묻는 것을 하나 더 나누는 정상적인 변경까지 막는다. 2절 원칙의 예외(설계가 성질로 정한 호출 여부)에 들지 않는 한, 정확한 횟수는 구현에 의존하는 단언이다.
* 같은 테스트 안에서 두 경우를 함께 돌려 견준다 — 어느 한쪽만 있으면 무엇과 같아야 하는지 모른다.

| 어디 | 무엇을 센다 |
|---|---|
| 유스케이스 | 가짜 의존성이 받은 호출 수. 가짜는 호출을 기록만 한다 (5절) |
| 의존성 구현 (통합) | 실제 DB 에 나간 질의 수. 연결에 질의 기록을 걸어 센다 |
| 화면 (`features`) | 가짜 서버 호출 수 |

**목록을 다루는 자리를 새로 만들 때 이 테스트를 함께 둔다.** 리팩토링 검사에서 N+1 을 찾아 고친 자리도 같다.

## 8. 규칙 ID 와 커버리지 검사

* **규칙마다 대응 테스트가 있다** (NFR-007). 설계서 4절의 테스트 사항이 그 목록이다.
* **규칙 ID 는 테스트 함수의 이름이나 문서 문자열에 적는다** — `test_qry_r005_...` 또는 `"""QRY-R005 ..."""`.
* **`tests/test_rule_coverage.py` 가 센다.** 설계서 3절 · 4절의 ID 가 같은 묶음인지, 모든 ID 가 테스트 이름 · 문서 문자열에 있는지, 설계서에 없는 ID 를 적지 않았는지 본다. **주석 · 가짜 · 보조 함수에 적힌 ID 는 세지 않는다.**
* **고정값에 실제 규칙 ID 를 쓰지 않는다.** 검사가 그것을 「덮였다」로 센다. 가짜 ID 는 `ZZZ-R001` 처럼 쓴다.
* **규칙 ID 가 없는 테스트도 있다.** 경계값 · 이상한 입력처럼 규칙은 아니지만 확인해야 하는 것들이다. 커버리지 검사는 규칙이 다 덮였는지만 본다.

## 9. 구조는 테스트로 지키지 않는다

「모델에 메서드가 없다」 · 「규칙이 의존성을 import 하지 않는다」 같은 것은 판정이 아니라 **구조 규칙**이다. 테스트로 쓰면 이름과 선언 순서에 기대게 되므로 **경계 검사**(서버 `import-linter`, 화면 ESLint)에 둔다.

## 10. 돌리는 법

`scripts/test.sh`(서버), `scripts/check.sh`(전체). 도구를 직접 부르지 않는다. 테스트가 깨지면 `skip` 하거나 기대값을 결과에 맞추지 않고 원인을 찾는다.

**테스트가 틀린 구현을 잡는지는 `scripts/mutate.sh` 로 기계로 확인한다.** 판단 코드(`backend/pyproject.toml` 의 `[tool.mutmut]`)를 비교 · 조건 · 값 · 반환마다 바꿔 보고, 테스트가 잡지 못한 변이를 보여 준다. 언제 돌리는지는 [검사 운영 규칙](review.md) 2절이 정한다. **살아남아도 되는 변이는 셋뿐이다. 그 밖이 살아남으면 테스트가 빠진 것이다.** 살아남은 것은 하나씩 이 셋 가운데 어디에 드는지 적어 보고한다.

* **문구만 바꾼 것** — 고정 문구, 바깥이 준 문구(오류 글), 설계서가 정하지 않은 이름의 글자. 문구는 3절대로 테스트하지 않는다(설계서가 정한 안내 낱말 밖의 글자를 바꾼 것).
* **`assert_never` 갈래를 바꾼 것** — 실행 중에는 닿지 않는 갈래라 테스트가 아니라 타입 검사(`mypy`)가 지킨다. 열거 값이 늘면 mypy 가 멈추는지 한 번 확인해 둔다.
* **동치 변이** — 바꿔도 밖에서 관찰되는 동작이 같은 것이다. 예: 지역에서만 쓰는 객체를 복사할지(`copy=`), 설계서가 「의미 없다」고 정한 값(분석 오류일 때 SQL 구성의 나머지 필드). 설계서가 정하지 않은 값을 테스트로 못박으면 구현에 의존하는 테스트가 되므로(1절), 잡지 않는 것이 맞다. **관찰할 길이 있으면 동치가 아니다** — 방언 · 형식처럼 다른 입력에서 드러나는지 먼저 찾아본다.
