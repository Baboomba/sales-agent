# 평가와 모델 선정

모델과 프롬프트는 느낌이 아니라 평가 세트의 숫자로 고른다 (NFR-006). 실행은 `eval` 스킬 · `scripts/eval.sh` 로 한다.

## 결론

**`qwen2.5-coder:1.5b` 를 기본 모델로 쓴다.** 정답률 85%, 받는 용량 약 1GB.

| 모델 | 용량 | 정답률 | 평균 시간 | 재생성률 |
|---|---:|---:|---:|---:|
| qwen2.5-coder:0.5b | 397MB | 35% | 3.0s | 20% |
| **qwen2.5-coder:1.5b** | **986MB** | **85%** | **5.2s** | **20%** |
| qwen2.5-coder:3b | 1.9GB | 90% | 3.6s | 10% |

**고른 기준: 정답률 80% 이상인 모델 가운데 가장 작은 것.** 검토자가 처음 실행할 때 모델을 받아야 하고(`requirements.md` 1절), GPU 가 없을 수 있다. 3b 는 5%p(한 문항) 더 맞히지만 받을 용량이 두 배다. 더 정확해야 하는 환경이면 `OLLAMA_MODEL=qwen2.5-coder:3b` 하나로 바꿀 수 있다.

## 방법

| 항목 | 내용 |
|---|---|
| 문항 | 20개 — `backend/evaluation/questions.yaml`. 매출 정의 · 집계 · 순위 · 날짜 · 조건 · 조인 |
| 정답 | 문항마다 정답 SQL. 직접 실행해 결과를 확인했다 |
| 판정 | 정답 SQL 결과의 열마다 같은 값의 열이 Agent 결과에 있고, 행 수가 같으면 정답. 순위 · 추이 문항은 순서까지 본다. Agent 가 열을 더 붙이는 것은 틀린 것으로 보지 않는다 |
| 정답률 | 실행 결과가 정답과 같은 문항의 비율 |
| 재생성률 | 첫 생성으로 끝나지 않은 문항의 비율 |
| 환경 | Apple M4 Max, Docker 안의 Ollama (GPU 없이 CPU) · temperature 0 |

## 경과

한 번에 고른 것이 아니다. 재고, 틀린 문항을 읽고, 고치고, 다시 쟀다.

| 차수 | 바꾼 것 | 0.5b | 1.5b | 3b |
|---|---|---:|---:|---:|
| 1차 | 첫 프롬프트 | 45% | 60% | 85% |
| 2차 | 정의 · 안내를 더하고, 예시 날짜를 프롬프트에 씀 | — | 60% | **70%** ↓ |
| 3차 | 프롬프트의 구체적인 날짜를 빼고 형식만 남김 | 35% | **85%** | **90%** |

### 1차 — 틀린 문항을 유형으로 나눴다

| 유형 | 문항 | 무엇이 틀렸나 | 대응 |
|---|---|---|---|
| 판정 오류 | E04 | 월을 `'2025-01'` 로 낸 답을 `'01'` 과 다르다고 봤다. 건수는 맞았다 | **평가 세트를 고쳤다** — 표기가 아니라 건수를 순서대로 본다 |
| 정의 | E13 | "주문 한 건당 평균" 을 상품 한 줄의 평균(`AVG`)으로 셌다 | 주문 건수 정의를 `data.md` 와 프롬프트에 넣었다 |
| SQLite 문법 | E18 | `strftime('%w')` 결과(문자열)를 숫자 `IN (0, 6)` 과 비교했다 | strftime 결과가 문자열이라는 안내를 넣었다 |
| 재생성 헛돎 | E10 · E12 | JOIN 없이 별칭(`o.`)을 쓰고, DB 오류만 받아서는 세 번 모두 같은 SQL 을 냈다 | `QRY-R015` — 오류에 "그 별칭의 표를 JOIN 하라" 를 덧붙인다 |
| 예시 베끼기 | 0.5b 다수 | 예시 SQL 의 `region = '서울'` 같은 조건을 질문과 상관없이 넣었다 | "질문에 없는 조건을 넣지 않는다" 를 넣었다 |

### 2차 — 고쳤더니 나빠졌다

3b 가 85% → 70% 로 떨어졌다. 틀린 SQL 을 읽어 보니 원인이 하나였다. **프롬프트의 안내 문장에 예로 든 날짜 범위(`'2025-01-01' AND '2025-06-30'`)를, 두 모델이 기간을 묻지 않은 질문에까지 그대로 넣었다.** 1차에서 0.5b 가 예시 조건을 베낀 것과 같은 현상이다.

반대로 1차에서 고치려 한 것은 고쳐져 있었다. E13 은 `COUNT(DISTINCT order_id)` 로 나눴고 E18 은 문자열로 비교했다 — 베낀 날짜 조건 때문에만 틀렸다.

**교훈: 작은 모델에게 주는 안내에는 구체적인 값을 쓰지 않는다. 형식만 쓴다.**

### 3차 — 날짜 값을 빼고 형식만 남겼다

1.5b 60% → 85%, 3b 85% → 90%. 0.5b 는 45% → 35% 로 오히려 떨어졌다 — 안내가 길어지자 따라오지 못했다. 0.5b 는 이 작업에 작다.

## 남은 오답

| 모델 | 문항 | 원인 | 판단 |
|---|---|---|---|
| 1.5b | E10 · E12 | JOIN 누락. `QRY-R015` 안내를 받고도 세 번 모두 같은 실수 | 안내만으로는 부족하다. 다음 단계는 규칙으로 고치는 것 — 검증 단계에서 FROM · JOIN 에 없는 별칭을 찾아 사유로 돌려주면 실행 전에 잡힌다 |
| 3b | E14 | 개점일(`stores.opened_on`) 대신 주문일로 거름 | 열 설명을 더 강조할 여지 |
| 둘 다 | E17 | "주문 상품 몇 건" 을 주문 수(`COUNT(DISTINCT order_id)`)로 셌다. 정답은 주문 상품 줄 수 | **질문이 모호하다.** 점수를 위해 문항을 고치지 않고 그대로 둔다. 실제 서비스라면 되묻기가 필요한 질문이다 |

## 이 측정의 한계

* **20문항이라 한 문항이 5%p 다.** 1.5b(85%)와 3b(90%)의 차이는 한 문항이다.
* **시간은 이 기계의 숫자다.** 검토자의 CPU 에서는 다르다. 재생성이 많을수록 길어져서, 1.5b 가 3b 보다 느리게 나온 것은 크기보다 재생성 횟수 탓이다.
* **temperature 0 으로 한 번씩 돌렸다.** 같은 입력에 같은 출력이 나오지만, 프롬프트가 조금만 바뀌어도 결과가 크게 흔들린다는 것을 2차에서 봤다. 프롬프트를 바꾸면 반드시 다시 잰다.
* **평가 세트를 보며 프롬프트를 고쳤다.** 고친 내용은 문항 맞춤이 아니라 데이터 정의(주문 건수 · strftime)와 일반 원칙(질문에 없는 조건 금지)이지만, 새 문항으로 다시 재면 숫자가 내려갈 수 있다.

## 다시 재는 방법

```bash
# 모델 서버를 호스트의 11434 로 띄운다 (Mac 이면 ollama serve 로 대신해도 된다)
docker run -d --name eval-ollama -p 11434:11434 -v eval-ollama:/root/.ollama ollama/ollama
docker exec eval-ollama ollama pull qwen2.5-coder:1.5b
scripts/eval.sh qwen2.5-coder:1.5b
```

문항별 결과(만든 SQL · 시간 · 시도 횟수)는 `backend/evaluation/results/<모델>.json` 에 남는다.
