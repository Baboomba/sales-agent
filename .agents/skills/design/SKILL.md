# 설계

설계서는 코드의 정본이다. 이 스킬은 설계서를 바꾸는 유일한 경로다.

## 순서

1. **근거를 찾는다.** 요청이 `docs/requirements.md` 의 어느 FR · NFR 에서 오는지 적는다. 없으면 요구사항부터 고칠지 사용자에게 묻는다. 요구사항에 없는 기능을 설계서에 넣지 않는다.
2. **영향을 본다.** 바뀌는 규칙 ID, 흐름(2.1), 질의 단계(2.2), 모델과 의존(5.1 · 5.2), 설정(5.3)을 나열한다.
3. **초안을 보여 준다.** 파일을 고치지 않고 바뀔 부분만 보여 준다.
   * 새 규칙은 다음 번호를 쓴다. 지운 번호는 다시 쓰지 않는다.
   * 규칙마다 "위반 시" 를 적는다. 무엇이 깨지는지 못 적으면 규칙이 아니다.
   * 규칙마다 4절 테스트 사항에 줄을 더한다. 층(규칙 · 유스케이스 · 의존성 · API · 통합)을 정한다.
   * 규칙이 판단하는 모델이 5절에 있는지 본다. 없으면 모델부터 더한다 — 모델이 모든 것의 기반이다.
4. **승인을 받는다.** 「반영해」를 받은 뒤에만 파일을 고친다.
5. **어긋남을 찾는다** ([검사 운영 규칙](../../../docs/convention/review.md) 2절). 바꾼 낱말 · 이름을 설계서 · 규칙 문서 · 코드에서 찾아(`grep`) 다른 뜻으로 남은 곳이 없는지 보고, 3절 규칙 문장과 4절 테스트 사항이 같은 사실을 말하는지 대조한다. 바꾼 설계를 따르는 코드 주석 · 문서 문자열도 함께 고친다.
6. **검사한다.** `scripts/check.sh` 를 돌린다. 테스트 사항에 더한 규칙이 아직 테스트로 덮이지 않았으면 커버리지 검사가 실패하는 것이 정상이다 — `implement` 스킬로 넘긴다.

**구현 차례를 시작하기 전에 남은 설계 결정을 모아 한 번에 끝낸다.** 경계값 · 대소문자 · 모호한 낱말 · 옛 코드에만 있는 동작이 대상이다. 구현 도중에 설계서를 고치면 그때마다 어긋난 곳이 새로 생긴다 (#40 차례 1).

## 쓰는 법

* 평이한 한국어. 용어는 먼저 정의하고 쓴다.
* 한 사실은 한 곳에만 적는다. 다른 문서가 같은 것을 말해야 하면 가리킨다.
* "왜" 를 적는다. 버린 대안이 있으면 버린 이유를 적는다 (`docs/architecture.md` 3절 형식).
