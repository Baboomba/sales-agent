# 테스트 규칙 검사

테스트가 **지켜야 할 것을 실제로 지키는지** 검사한다. 테스트가 통과하는지는 보지 않는다(그것은 `scripts/test.sh`). 통과하는 테스트 가운데 틀린 코드도 통과시키는 것, 고칠 필요 없는 변경에 깨지는 것, 같은 것을 두 번 보는 것, 봐야 할 것을 안 보는 것을 찾는다.

**기준은 [테스트 규칙](../../../docs/convention/testing.md)이다.** 이 스킬은 어떻게 찾는지만 적고, 규칙을 여기서 다시 정하지 않는다.

## 서브 에이전트로 돌 때

implement 스킬이 이 스킬을 서브 에이전트에게 맡긴다. 서브 에이전트는 구현한 맥락을 모른 채 **규칙 문서와 코드만** 보고 판정한다.

* **작업 트리를 바꾸지 않는다.** 파일을 고치지 않는다. 일부러 망가뜨려 볼 때는 임시 작업 트리에서 한다 (아래).
* **근거를 붙인다.** 지적마다 `파일:줄` 과, 무엇을 보고 그렇게 판단했는지를 적는다. 확인하지 못한 것은 지적하지 않는다.
* 맡긴 쪽이 준 **모드**를 따른다 — 「규칙 위반」(테스트를 쓴 뒤) 또는 「빠진 테스트」(구현을 마친 뒤). 말이 없으면 둘 다 본다.
* **지적마다 심각도(상 · 중 · 하)를 붙인다** — [검사 운영 규칙](../../../docs/convention/review.md) 4절. 가르는 질문은 「이 틀린 구현을 사람이 실수로 쓸 법한가」다. 일부러가 아니면 쓰지 않을 억지 변이로만 드러나는 것은 하도 아니고 **보고하지 않는다** (아래 「보고」의 거르기).
* **맡긴 쪽이 준 판단 기록에 있는 것은 다시 지적하지 않는다.** 새 근거가 있을 때만 그 근거와 함께 다시 꺼낸다.
* **보는 것은 설계서 4절의 확인 사항과 이번 차례의 코드 · 테스트다.** 바깥 도구를 무작위 입력으로 찔러 우회를 찾는 탐색은 하지 않는다 — 보안 감사의 몫이다 (검사 운영 규칙 3절).
* **옛 코드에서 그대로 넘어온 결함**(옛 코드도 같은 입력에 같은 결과를 냄)을 우연히 보면 표가 아니라 「범위 밖 — 넘어온 결함」으로 따로 적는다. 이 차례를 막지 않고 이슈로 빠진다 (검사 운영 규칙 4절).
* **변이 테스트 결과(`scripts/mutate.sh`)를 받았으면** 도구가 이미 잡은 꼴(비교 · 조건 · 값 · 반환 바꾸기)은 다시 망가뜨려 보지 않는다. 도구가 만들지 않는 꼴 — 찾을 대상의 자리, 입력 고르기, 값 하나로만 보기, 설계서와의 대조, 중복 — 에 힘을 쓴다.

## 흐름

1. **범위를 정한다** — 아래 「검사 범위」.
2. **읽는다** — 범위 안의 코드와 그 테스트를 **둘 다** 읽는다. 설계서 4절 테스트 사항도 읽는다. 테스트만 읽으면 무엇이 빠졌는지 모른다.
3. **네 가지로 가른다** — 아래 「검사 기준」. 의심 가는 것은 「일부러 망가뜨려 확인하기」로 확인한다.
4. **보고하고 멈춘다** — 아래 「보고」. 고치지 않는다.

## 검사 범위

말이 없으면 **지금 분기가 `main` 과 달라진 곳**이다. 커밋하지 않은 것도 넣는다.

```bash
git diff --name-only main...HEAD
git status --short
```

* 바뀐 **코드** 파일마다 그 테스트를 찾는다 — 서버 `backend/tests/<도메인>/<계층>/`, 화면 묶음 옆 `*.test.tsx` · `__test__/`.
* 바뀐 코드를 **가져다 쓰는 쪽의 테스트**도 본다. 중복 검사의 대상이다.
* 맡긴 쪽이 범위를 좁히거나 넓히면 그대로 따른다.
* **다시 검사면 범위는 맡긴 쪽이 준 `scripts/review-scope.sh diff` 의 결과(고친 줄)다.** 그 줄을 쓰는 테스트 · 코드는 읽어도 되지만, 지적은 고친 줄에서 생긴 것만 한다 (검사 운영 규칙 3절).

## 검사 기준

### 1. 구현에 의존하는 테스트 — 「규칙 위반」 모드

**판정 질문: 동작은 그대로 두고 안쪽만 바꾸면 이 테스트가 깨지는가.** 깨지면 위반이다.

* 내부 호출 순서 · 횟수를 단언한다. 단, 설계가 성질로 정한 것(테스트 규칙 2절 예외)은 위반이 아니다.
* 비공개 함수 · 내부 자료구조 · 구현이 쓰는 상수 · 문구와 견준다.
* 가짜에 판단이 들어 있어 가짜가 맞는지를 확인하는 테스트가 됐다.
* 테스트끼리 순서 · 남은 상태에 기댄다.

### 2. 빠진 테스트 — 「빠진 테스트」 모드

**판정 질문: 이 갈래를 반대로 바꿔도 어느 테스트가 깨지는가.** 아무것도 깨지지 않으면 빠진 것이다.

* 갈래의 양쪽, `except`, 빈 값, 경계값(상한 그 값 · 하나 넘은 값), 열거 값마다 하나씩 짚는다 (테스트 규칙 6절).
* 설계서 4절의 규칙 ID 마다 그 사실을 실제로 확인하는 테스트가 있는지 맞춰 본다. **ID 만 적혀 있고 그 판정을 보지 않으면 빠진 것이다.**
* 바깥이 있어야 보이는 것(읽기 전용 · 제한 시간)이 가짜로만 덮였다.
* 목록을 다루는 자리에 N+1 테스트(테스트 규칙 7.3)가 없다.
* **닿을 수 없는 갈래는 빠진 테스트가 아니라 지울 코드다** — 리팩토링 검사로 넘긴다고 적는다.

### 3. 중복 테스트 — 두 모드 모두

**판정 질문: 이 테스트를 지워도 다른 테스트가 같은 결함을 잡는가.** 잡으면 중복이다.

* 규칙의 판정을 유스케이스 · API 테스트가 경우를 늘어놓고 다시 본다. 위 계층은 흐름 · 연결만 하나 보면 된다.
* 같은 동작을 두 테스트가 다른 이름으로 본다.

### 4. 틀린 구현도 통과하는 테스트 — 두 모드 모두

**판정 질문: 대상 코드를 틀리게 바꿔도 이 테스트가 통과하는가.** 통과하면 위반이다 (테스트 규칙 4절).

* 참 거짓만 본다 — `assert result`, 사유를 `is not None` 으로만 본다.
* 입력 · 고정 문구에 원래 있는 글자를 찾는다.
* 짝 없는 「없다」 · 「비었다」 · 「통과한다」.
* 입력이 기본값 · 실제 값과 같아 박아 둔 구현과 가르지 못한다.
* 찾을 대상이 목록의 한 자리(대개 끝)에만 있다.
* 판정에 쓰여야 할 필드가 아닌 다른 필드에서도 같은 답이 나온다.
* 기대값을 계산하거나 출력에 맞춰 적었다.
* 실제로 올 수 없는 입력으로 흉내 내 남은 갈래로 통과한다.
* 환경 때문에 저절로 참이 된다.

## 일부러 망가뜨려 확인하기

2번(빠진 것)과 4번(틀린 구현도 통과)은 **이것 없이 단정하지 않는다.** 작업 트리를 건드리지 않도록 임시 작업 트리에서 한다.

```bash
git worktree add --detach "$TMPDIR/test-review" HEAD
```

1. 임시 작업 트리에서 대상 코드 한 곳만 틀리게 바꾼다 — 갈래 뒤집기, 조건 빼기, 값 바꾸기.
2. 그 테스트만 돌린다 — 서버는 `scripts/test.sh <테스트 파일>`, 화면은 `npx vitest run <테스트 파일>`.
3. 끝나면 임시 작업 트리를 지운다 — `git worktree remove --force "$TMPDIR/test-review"`.

커밋하지 않은 변경이 범위에 있으면, 임시 작업 트리에 그 파일들을 복사한 뒤 망가뜨린다.

보고에 「무엇을 어떻게 망가뜨렸더니 깨졌다 / 안 깨졌다」를 적는다.

## 보고

찾은 것을 표 하나로 보고한다. 고칠 방법까지 적되 **고치지 않는다.**

**표에 넣기 전에 거른다** ([검사 운영 규칙](../../../docs/convention/review.md) 4.1). 지적마다 두 질문을 묻고, 하나라도 「아니다」면 보고하지 않는다.

1. **실제로 일어날 법한가** — 작은 모델이 실제로 낼 입력, 사람이 실제로 쓸 법한 틀린 구현에서 생기는가. 일부러 꾸민 억지 변이 · 쓸 일 없는 입력 · 결과가 같은 것은 「아니다」.
2. **문제인가** — 설계서 · 규칙 문서를 어기거나 틀린 동작 · 보안 빈틈으로 이어지는가. 설계서가 정하지 않은 값 · 순서 · 문구, 취향은 「아니다」.

거른 것은 건수만 한 줄로 적는다(「거른 것 N건」). 애매하면 거른다.

| # | 심각도 | 종류 | 어디 | 무엇이 문제인가 | 근거 (망가뜨려 본 결과 등) | 고칠 방법 |
|---|---|---|---|---|---|---|
| T1 | 중 | 틀린 구현도 통과 | `backend/tests/…:42` | 고정 문구에 원래 있는 `"JOIN"` 을 찾는다 | 안내를 붙이지 않게 바꿔도 통과했다 — 안내를 빠뜨리는 것은 쓸 법한 실수다 | 테스트가 넣은 별칭으로 확인한다 |

* 표는 심각도 순(상 → 중 → 하)으로 놓는다. 심각도마다 **왜 그 등급인지** 근거 칸에 한마디 적는다.
* 네 종류마다 **찾은 것이 없으면 없다고, 무엇을 보고 그렇게 판단했는지** 한 줄씩 적는다. 빈칸이면 안 본 것인지 없는 것인지 모른다.
* 범위 밖에서 같은 문제를 봤으면 따로 적고, 이 분기에서 고칠지 이슈로 뺄지 권한다.
* 마지막 줄에 「고칠지 『고쳐』로 알려 주세요」.

## 고칠 때 (「고쳐」를 받은 뒤)

* **상 · 중만 고친다.** 하는 판단 기록에 남긴다 (검사 운영 규칙 4 · 6절).
* **지적은 꼴로 고친다** (테스트 규칙 4절). 지적된 줄만 고치지 않고, 같은 꼴을 범위의 모든 테스트에서 찾아 함께 고친다. 보고에는 꼴마다 어디를 고쳤는지 적는다.
* **고친 줄에도 대조 목록을 다시 묻는다** (검사 운영 규칙 2절). 고치면서 새 하자를 만들지 않는다.
* 고친 테스트는 **다시 망가뜨려 확인**한다 — 이번에는 결함을 잡는지.
* 중복을 걷어낼 때는 남는 쪽이 그 결함을 정말 잡는지 먼저 본다.
* 기대값을 출력에 맞추지 않는다. `skip` 으로 덮지 않는다.
* 끝나면 `scripts/check.sh` 를 돌리고 테스트 개수 변화를 보고한다.
