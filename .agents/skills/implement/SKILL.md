# 구현

한 차례는 설계서의 규칙 하나 또는 흐름 하나다. 여러 규칙을 한꺼번에 하지 않는다.

코드를 쓰기 전에 작업 경로의 규칙 파일과 정본을 읽는다 — `AGENTS.md` 「코드를 쓰기 전에」.

## 흐름

| 순서 | 단계 | 누가 |
|---|---|---|
| 1 | 설계서 검토 | 이 에이전트 |
| 2 | 테스트 작성 | 이 에이전트 |
| 3 | 테스트 규칙 검사 — `test-review` (규칙 위반) | **서브 에이전트** |
| 4 | 실패 확인 → ⏸ **승인 1** | 사람 |
| 5 | 구현 → `scripts/check.sh` | 이 에이전트 |
| 6 | 리팩토링 검사 — `refactor-review` | **서브 에이전트** |
| 7 | 테스트 규칙 검사 — `test-review` (빠진 테스트) | **서브 에이전트** |
| 8 | 지적을 나눠 보고 → ⏸ **승인 2** | 사람 |

### 1. 설계서 검토

* `docs/design/` 에서 대상 규칙(3절)과 테스트 사항(4절)을 찾는다. 판단하는 모델이 5절에 있는지 본다.
* 그 규칙이 `docs/requirements.md` 의 어느 요구사항에서 오는지 확인한다.
* **없거나 어긋나면 멈추고** `design` 스킬로 넘긴다. 설계서에 없는 것을 구현하지 않는다.

### 2. 테스트 작성

* 테스트 사항 표의 「확인」을 그대로 테스트로 옮긴다. 자리는 계층에 따른다 ([테스트 규칙](../../../docs/convention/testing.md) 7절).
* 규칙 ID 를 테스트 이름이나 문서 문자열에 적는다.
* 목록을 다루는 자리면 N+1 테스트를 함께 쓴다 (테스트 규칙 7.3).

### 3. 테스트 규칙 검사 — 서브 에이전트

`test-review` 를 **「규칙 위반」 모드**로 서브 에이전트에게 맡긴다 (아래 「서브 에이전트에게 맡기는 법」). 범위는 2단계에서 쓴 테스트다.

### 4. 실패 확인 → ⏸ 승인 1

* `scripts/test.sh` 로 돌려 **새 테스트가 기대한 이유로** 실패하는지 본다. import 오류로 실패하는 것은 기대한 실패가 아니다.
* 보고한다 — 쓴 테스트 목록과 각 테스트가 확인하는 사실, 실패한 이유, **3단계 검사 결과를 그대로.**
* 「고쳐」를 받으면 테스트를 고치고 3단계부터 다시 한다.
* **승인 전에는 구현하지 않는다.** 구현하면서 승인받은 테스트를 고치지 않는다.

### 5. 구현 → 검사

* 테스트를 통과하는 가장 단순한 코드를 쓴다. 설계서에 없는 동작을 더하지 않는다.
* 계층은 [코드 아키텍처](../../../docs/convention/code-architecture.md)를 따른다 — 판단은 규칙에, 바깥은 의존성 구현에.
* `scripts/check.sh` 전체가 통과해야 한다 — 린트 · 포맷 · 타입 · 계층 경계 · 규칙 커버리지 · 테스트.
* 구현이 설계서와 어긋난 곳이 생기면 코드가 아니라 설계서가 맞는지부터 사용자에게 묻는다.

### 6. 리팩토링 검사 — 서브 에이전트

`refactor-review` 를 서브 에이전트에게 맡긴다. 범위는 이 분기가 `main` 과 달라진 곳이다.

### 7. 테스트 규칙 검사 — 서브 에이전트

`test-review` 를 **「빠진 테스트」 모드**로 서브 에이전트에게 맡긴다. 6단계와 서로 기다릴 일이 없으므로 **함께 띄운다.**

### 8. 나눠 보고 → ⏸ 승인 2

* 6 · 7단계의 지적을 합쳐 **이 분기에서 고칠 것 / 따로 뺄 것 / 그대로 두기를 권함** 으로 나눈다 ([리팩토링 규칙](../../../docs/convention/refactoring.md) 2절).
* 보고한다 — 바뀐 파일, `scripts/check.sh` 결과, 설계와 어긋난 점, 나눈 지적. **검사 결과를 빼거나 줄이지 않는다.**
* 「고쳐」를 받으면 고치고, 고친 범위에 대해 6 · 7단계를 다시 한다. 따로 뺄 것은 이슈를 만들지 묻는다.
* **승인이 곧 커밋 지시다.** 승인 전에는 커밋하지 않는다.

## 서브 에이전트에게 맡기는 법

**검사를 구현한 에이전트가 하지 않는다.** 자기가 짠 의도대로 읽어서 놓친다. 구현 맥락이 없는 서브 에이전트가 규칙 문서와 코드만 보고 판정한다.

맡길 때 넘기는 것은 넷이다.

1. 읽을 스킬 — `.agents/skills/<test-review | refactor-review>/SKILL.md` 를 읽고 그대로 하라
2. 모드 — `test-review` 면 「규칙 위반」 또는 「빠진 테스트」
3. 범위 — 파일 목록, 또는 「이 분기가 `main` 과 달라진 곳」
4. 제한 — **파일을 고치지 마라.** 근거(`파일:줄`)를 붙여 스킬의 보고 표로 돌려 달라

구현 맥락(왜 이렇게 짰는지, 무엇을 의도했는지)은 **넘기지 않는다.**

| 에이전트 | 맡기는 방법 |
|---|---|
| Claude Code | 서브 에이전트 도구(`Agent`)로 띄운다. 6 · 7단계는 한 번에 둘을 띄운다 |
| Codex | 서브 에이전트 기능이 있으면 그것으로 띄운다. 없으면 멈추고, 사용자에게 **새 세션에서** 그 스킬을 돌려 결과를 붙여 달라고 요청한다 — 같은 세션에서 스스로 검사하지 않는다 |

서브 에이전트의 보고는 **그대로** 사용자에게 전한다. 맞지 않는다고 보는 지적이 있으면 빼지 말고, 왜 그렇게 보는지 옆에 적는다.

## 금지

* 승인 두 자리를 건너뛰기 — 사용자가 「그냥 진행해」라고 해도 건너뛰지 않는다 (`AGENTS.md`)
* 검사를 스스로 하기 — 3 · 6 · 7단계는 서브 에이전트의 일이다
* 테스트를 결과에 맞춰 고치기, `skip`, 검사 우회 — `AGENTS.md` 「검사를 우회하지 않는다」
* 언어 모델을 부르는 테스트 — 모델 품질은 `eval` 스킬이 잰다
