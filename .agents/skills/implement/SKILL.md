# 구현

한 차례는 설계서의 규칙 하나 또는 흐름 하나다. 여러 규칙을 한꺼번에 하지 않는다. **차례를 나눠 제안할 때도 같다** — 한 차례에 규칙 여럿을 묶은 계획을 내지 않는다. 묶으면 검사 한 번이 볼 것이 많아지고, 하나를 고칠 때마다 옆 규칙으로 번진다(#40 차례 1, [검사 운영 규칙](../../../docs/convention/review.md) 1절).

코드를 쓰기 전에 작업 경로의 규칙 파일과 정본을 읽는다 — `AGENTS.md` 「코드를 쓰기 전에」. 검사를 굴리는 법은 [검사 운영 규칙](../../../docs/convention/review.md)이 정본이다.

## 흐름

| 순서 | 단계 | 누가 |
|---|---|---|
| 1 | 설계서 검토 · 판단 기록에서 미룬 것 꺼내기 | 이 에이전트 |
| 2 | 테스트 작성 → **자기 확인** → 실패 확인 | 이 에이전트 |
| 3 | 구현 → `scripts/check.sh` → `scripts/mutate.sh` → **자기 확인** | 이 에이전트 |
| 4 | 검사 한 번 — `refactor-review` · `test-review` (규칙 위반 · 빠진 테스트) 를 함께 띄운다 | **서브 에이전트** |
| 5 | 상 · 중을 고치고 직접 확인 → 상을 고쳤으면 고친 줄만 다시 검사 한 번 | 이 에이전트 · 서브 에이전트 |
| 6 | 심각도로 나눠 보고 → ⏸ **승인** | 사람 |

**승인은 한 번이다.** #40 은 차례마다 승인 두 번 · 검사 4~6번을 거쳐 이슈 하나에 다섯 시간이 넘게 걸렸다 (#52). 검사 대기와 멈춤을 줄이고, 그 대신 자기 확인과 변이 테스트로 먼저 거른다.

### 1. 설계서 검토

* `docs/design/` 에서 대상 규칙(3절)과 테스트 사항(4절)을 찾는다. 판단하는 모델이 5절에 있는지 본다.
* 그 규칙이 `docs/requirements.md` 의 어느 요구사항에서 오는지 확인한다.
* **없거나 어긋나면 멈추고** `design` 스킬로 넘긴다. 설계서에 없는 것을 구현하지 않는다.
* **설계서가 없는 영역**(`scripts/` · 훅 · 설정 같은 장치, 화면 설계서가 생기기 전의 화면)은 **이슈 본문이 근거다.** 설계서 검토 대신 이슈의 「무엇을」 · 「끝났다고 볼 기준」을 읽고, 그 기준을 테스트 사항으로 삼는다. 기준이 없으면 이슈에 먼저 적는다(사용자 확인).
* **설계 결정이 남았는지 여기서 끝까지 본다** — 경계값(음수 · 0 · 빈 값), 대소문자, 모호한 낱말, 옛 코드의 동작 가운데 설계서에 없는 것. 남았으면 테스트를 쓰기 전에 `design` 스킬로 끝낸다. 차례 도중에 설계서를 고치면 그때마다 어긋난 곳이 새로 생긴다.
* 이슈의 「판단 기록」 댓글에서 **이 차례로 미뤄 둔 것**을 꺼내 먼저 본다 (검사 운영 규칙 6절).

### 2. 테스트 작성 → 자기 확인 → 실패 확인

* 테스트 사항 표의 「확인」을 그대로 테스트로 옮긴다. 자리는 계층에 따른다 ([테스트 규칙](../../../docs/convention/testing.md) 7절).
* 규칙 ID 를 테스트 이름이나 문서 문자열에 적는다.
* 목록을 다루는 자리면 N+1 테스트를 함께 쓴다 (테스트 규칙 7.3).
* **다 쓰면 새로 쓴 줄마다 검사 운영 규칙 2절의 대조 목록을 묻는다.** 걸리는 것은 바로 고친다.
* `scripts/test.sh` 로 돌려 **새 테스트가 기대한 이유로** 실패하는지 본다. import 오류로 실패하는 것은 기대한 실패가 아니다 — 겉모양만 있는 자리표시를 먼저 둔다.

### 3. 구현 → 검사 도구 → 자기 확인

* 테스트를 통과하는 가장 단순한 코드를 쓴다. 설계서에 없는 동작을 더하지 않는다.
* 계층은 [코드 아키텍처](../../../docs/convention/code-architecture.md)를 따른다 — 판단은 규칙에, 바깥은 의존성 구현에.
* **옛 코드에서 옮긴 동작은 설계서 3절 문장과 하나씩 대조한다.** 문구 · 접두어 하나라도 설계서와 다르면 코드가 아니라 설계서가 맞는지부터 사용자에게 묻는다.
* `scripts/check.sh` 전체가 통과해야 한다 — 린트 · 포맷 · 타입 · 계층 경계 · 규칙 커버리지 · 테스트.
* **`scripts/mutate.sh` 를 돌린다** (바뀐 함수만 — 수 초). 살아남은 변이를 하나씩 테스트 규칙 10절의 세 갈래(문구 · `assert_never` 갈래 · 동치 변이)에 넣어 보고, 어디에도 들지 않는 것이 있으면 테스트를 더한다. 더한 뒤에는 `scripts/mutate.sh --recheck` 로 살아남은 변이를 다시 돈다. 더한 테스트에도 대조 목록을 묻는다.
* 「mypy 가 잡는다」 같은 말은 **실행해서 확인한 뒤에만** 한다.

### 4. 검사 한 번 — 서브 에이전트

맡기기 **직전에** `scripts/review-scope.sh mark` 로 기준점을 남긴다. `refactor-review` 와 `test-review`(「규칙 위반」 · 「빠진 테스트」 두 모드)를 **한 번에 함께 띄운다** (아래 「서브 에이전트에게 맡기는 법」). 범위는 이번 차례의 코드 · 테스트다. `scripts/mutate.sh` 의 살아남은 변이도 함께 넘긴다 — 검사자가 도구가 이미 잡은 꼴을 되풀이하지 않고, 도구가 만들지 않는 꼴(자리 · 입력 고르기 · 설계서 대조)에 힘을 쓰게 한다.

### 5. 고치기 → 확인

* 지적을 **심각도(상 · 중 · 하)** 로 나눈다 ([검사 운영 규칙](../../../docs/convention/review.md) 4절). **상 · 중은 묻지 않고 고친다. 하는 고치지 않고 판단 기록에 남긴다.** 설계서가 바뀌는 지적만 사용자에게 먼저 묻는다.
* 지적된 줄만이 아니라 **같은 꼴을 이번 차례의 모든 테스트 · 코드에서** 찾아 고치고, 고친 줄에도 대조 목록을 묻는다.
* 고친 것은 **직접 확인한다** — 지적이 말한 틀린 구현을 임시 사본에 넣어 테스트가 잡는지 보고, `scripts/check.sh` · `scripts/mutate.sh --recheck` 를 돈다.
* **상을 고쳤을 때만** 고친 줄을 한 번 다시 검사한다 (`scripts/review-scope.sh diff`). 중만 고쳤으면 다시 검사하지 않는다. 다시 검사 뒤에 남은 것은 더 돌리지 않고 보고한다.
* **이번 차례가 만들거나 건드린 것이 아니면 상이라도 이 차례를 막지 않는다.** 옛 코드도 같은 입력에 같은 결과를 냈으면 넘어온 결함이다 — 이슈로 뺀다.

### 6. 보고 → ⏸ 승인

* 보고한다 — 바뀐 파일, `scripts/check.sh` · `scripts/mutate.sh` 결과, 검사 지적과 처리(고침 · 하 · 이슈로 뺌 · 거름 건수), 설계와 어긋난 점. **검사 결과를 빼거나 줄이지 않는다.**
* **승인이 곧 커밋 지시다.** 승인을 받으면 이슈의 「판단 기록」 댓글을 고쳐 쓰고 커밋한다. 승인 전에는 커밋하지 않는다.
* PR 을 열기 전에는 `scripts/mutate.sh --full` 로 처음부터 돈다 — 증분 실행은 테스트를 지우거나 약하게 바꾼 것을 보지 못한다.

## 서브 에이전트에게 맡기는 법

**검사를 구현한 에이전트가 하지 않는다.** 자기가 짠 의도대로 읽어서 놓친다. 구현 맥락이 없는 서브 에이전트가 규칙 문서와 코드만 보고 판정한다. 다만 **자기 확인(2 · 3단계)은 검사가 아니라 넘기기 위한 준비다** — 건너뛰지 않는다.

맡길 때 넘기는 것은 여섯이다.

1. 읽을 스킬 — `.agents/skills/<test-review | refactor-review>/SKILL.md` 를 읽고 그대로 하라
2. 모드 — `test-review` 면 「규칙 위반 · 빠진 테스트 둘 다」
3. 범위 — 첫 검사면 파일 목록, **다시 검사면 `scripts/review-scope.sh diff` 의 결과**
4. 판단 기록 — 이미 받아들인 것 · 하로 둔 것 · 다른 차례로 미룬 것. **다시 지적하지 마라, 새 근거가 있을 때만 근거와 함께**
5. 참고 결과 — `scripts/mutate.sh` 의 살아남은 변이
6. 제한 — **파일을 고치지 마라.** 지적마다 근거(`파일:줄`)와 **심각도(상 · 중 · 하)** 를 붙여 스킬의 보고 표로 돌려 달라. **보고 전에 거르라** — 실제로 일어날 법하지 않거나 문제가 아닌 것은 넣지 말고 건수만 적어라 ([검사 운영 규칙](../../../docs/convention/review.md) 4.1)

서브 에이전트의 보고를 받으면 **맡긴 쪽도 같은 두 질문으로 다시 거른다.** 걸러야 할 것이 올라왔으면 고치지 않고 보고에 「거름」으로 적는다.

구현 맥락(왜 이렇게 짰는지, 무엇을 의도했는지)은 **넘기지 않는다.**

| 에이전트 | 맡기는 방법 |
|---|---|
| Claude Code | 서브 에이전트 도구(`Agent`)로 띄운다. 4단계는 둘을 한 번에 띄운다 |
| Codex | 서브 에이전트 기능이 있으면 그것으로 띄운다. 없으면 멈추고, 사용자에게 **새 세션에서** 그 스킬을 돌려 결과를 붙여 달라고 요청한다 — 같은 세션에서 스스로 검사하지 않는다 |

## 금지

* 승인을 건너뛰기 — 사용자가 「그냥 진행해」라고 해도 커밋 전 승인은 받는다 (`AGENTS.md`)
* 검사를 스스로 하기 — 4단계는 서브 에이전트의 일이다
* 자기 확인 없이 검사에 넘기기 — 2 · 3단계의 대조 목록과 `scripts/mutate.sh`
* 실행하지 않고 단정하기 — 「잡는다」 「통과한다」는 실행 결과가 있을 때만
* 다시 검사에 범위 전체를 넘기기, 상이 아닌데 다시 검사하기, 옛 코드에서 넘어온 결함으로 차례를 붙잡기
* 테스트를 결과에 맞춰 고치기, `skip`, 검사 우회 — `AGENTS.md` 「검사를 우회하지 않는다」
* 언어 모델을 부르는 테스트 — 모델 품질은 `eval` 스킬이 잰다
