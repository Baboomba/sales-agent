# 리팩토링 검사

동작은 그대로 두고 **구조만 나아질 곳**을 찾는다. 기능을 더하거나 바꾸는 제안은 하지 않는다.

**기준은 [리팩토링 규칙](../../../docs/convention/refactoring.md)과 [코드 아키텍처](../../../docs/convention/code-architecture.md) · [코드 컨벤션](../../../docs/convention/code-style.md)이다.** 이 스킬은 어떻게 찾는지만 적고, 규칙을 여기서 다시 정하지 않는다.

## 서브 에이전트로 돌 때

implement 스킬이 이 스킬을 서브 에이전트에게 맡긴다. 서브 에이전트는 구현한 맥락을 모른 채 **규칙 문서와 코드만** 보고 판정한다. 구현한 쪽은 자기가 짠 의도대로 읽어서 놓친다.

* **작업 트리를 바꾸지 않는다.** 파일을 고치지 않는다.
* **근거를 붙인다.** 지적마다 `파일:줄` 과, 리팩토링 규칙의 어느 판정 질문에 어떻게 답했는지를 적는다. 질문에 답할 수 없으면 지적하지 않는다.
* **지적마다 심각도(상 · 중 · 하)를 붙인다** — [검사 운영 규칙](../../../docs/convention/review.md) 4절. 틀린 동작 · 보안 · 설계서와 어긋남은 상, 이 분기가 만든 구조 문제는 중, 취향 · 일어날 법하지 않은 경우만 걸리는 것은 하다.
* **맡긴 쪽이 준 판단 기록에 있는 것은 다시 지적하지 않는다.** 새 근거가 있을 때만 그 근거와 함께 다시 꺼낸다.
* **확인한 것만 단정한다.** 「도구가 잡는다 / 못 잡는다」는 실제로 돌려 본 뒤에 적는다.

## 흐름

1. **범위를 정한다** — 아래 「검사 범위」.
2. **읽는다** — 범위 안의 코드와, 그것과 **같은 꼴을 가진 다른 곳**을 함께 읽는다. 중복과 공용 코드는 범위 밖과 견줘야 보인다.
3. **여섯 가지로 가른다** — 아래 「검사 기준」.
4. **나눈다** — 이 분기에서 고칠 것 / 따로 뺄 것 / 그대로 두기를 권함 (리팩토링 규칙 2절).
5. **보고하고 멈춘다** — 고치지 않는다.

## 검사 범위

말이 없으면 **지금 분기가 `main` 과 달라진 곳**이다. 커밋하지 않은 것도 넣는다.

```bash
git diff --name-only main...HEAD
git status --short
```

* 바뀐 파일은 **전체를** 읽는다. 바뀐 줄만 보면 옆에 남은 사본을 놓친다.
* 같은 꼴은 이름 · 문구 · 모양으로 저장소 전체에서 찾는다 (예: 같은 사유 문구, 같은 함수 모양).
* 맡긴 쪽이 범위를 좁히거나 넓히면 그대로 따른다.
* **다시 검사면 범위는 맡긴 쪽이 준 `scripts/review-scope.sh diff` 의 결과(고친 줄)다.** 같은 꼴을 찾으려고 다른 곳을 읽어도 되지만, 지적은 고친 줄에서 생긴 것만 한다 (검사 운영 규칙 3절).

## 검사 기준

리팩토링 규칙 1절의 여섯 항목이다. 항목마다 그 판정 질문으로 판단한다. 아래는 이 저장소에서 특히 볼 자리다.

| 항목 | 특히 볼 자리 |
|---|---|
| **1. 단일 책임** | 판단이 규칙 밖(유스케이스 · 의존성 구현 · API)에 있다 · 모델에 메서드가 있다 · 규칙이 바깥 글(SQL · 오류 문구 · 출력 형식)을 해석한다 · 모델이 바깥 모양을 따른다 · 화면 계층을 건너뛴다(`entities` 의 서버 호출, `features` 의 `.tsx` 안 훅 정의) |
| **2. 비효율** | 같은 스키마 · 분석을 두 번 묻는다 · 기다릴 일 없는 바깥 호출을 차례로 기다린다 |
| **3. 쓰이지 않는 분기** | 앞에서 이미 막은 갈래 · 타입상 늘 있는 값의 대체값 · 쓰이지 않는 함수 · 상수 · 내보내기 · 스타일 클래스 |
| **4. 심각한 하자** | **N+1** (리팩토링 규칙 1.4 「N+1」 — 반복 · `map` · 컴프리헨션 속까지 따라가 바깥 호출에 닿는지) · 실패 삼키기 · 넓은 `except` 가 입구 밖에 있음 · 바깥 예외가 의존성 구현 밖으로 샘 · 박아 둔 수 · 모델이 낸 SQL 을 판정 전에 씀 |
| **5. 공용 코드** | `components` · `common/values.ts` · 공용 함수에 이미 있는 일을 다시 한다 |
| **6. 중복** | 같은 코드 · 상수 · 문구가 두 곳 이상. 세 벌이면 뽑고, 두 벌이면 따져 권한다 |

**동작이 바뀌는 제안은 하지 않는다.** 응답 모양 · 사유 문구 · 이벤트 순서가 바뀌면 리팩토링이 아니다.

## 보고

| # | 심각도 | 종류 | 어디 | 무엇 | 판정 질문과 답 | 권하는 것 | 갈래 |
|---|---|---|---|---|---|---|---|
| R1 | 상 | 심각한 하자 (N+1) | `backend/app/…:31` | 표마다 열 정보를 따로 묻는다 | 표가 1개면 2번, 5개면 6번 — 같지 않다 | 한 번에 묻고 메모리에서 나눈다 | 이 분기 |

* 표는 심각도 순(상 → 중 → 하)으로 놓는다.
* 여섯 종류마다 **찾은 것이 없으면 없다고, 무엇을 보고 그렇게 판단했는지** 한 줄씩 적는다.
* 고치면 설계서가 바뀌는 것(의존성의 모양 · 모델)은 그렇다고 적는다.
* 마지막 줄에 「고칠지 『고쳐』로 알려 주세요」. 따로 뺄 것이 있으면 이슈를 만들지도 함께 묻는다.

## 고칠 때 (「고쳐」를 받은 뒤)

리팩토링 규칙 3절을 따른다.

* **상 · 중만 고친다.** 하는 판단 기록에 남긴다 (검사 운영 규칙 4 · 6절).
* **동작을 바꾸지 않는다.** 기존 테스트를 고쳐야 통과한다면 동작이 바뀐 것이다 — 멈추고 알린다.
* 인터페이스가 바뀌면 가짜와 테스트를 함께 맞춘다.
* 고친 갈래에 테스트가 없으면 더하고, `test-review` 의 「일부러 망가뜨려 확인하기」로 그 테스트가 깨지는지 본다.
* 설계서가 바뀌어야 하면 설계서부터 고친다 (`design` 스킬, 사용자 확인).
* 끝나면 `scripts/check.sh` 를 돌린다.
